# Productization Target

## 扫描结论

当前仓库已经具备较强的写作、检索、导出与流程编排能力，但产品层仍存在典型“练手项目”信号：

1. 首页虽然已转为控制台，但还需要继续强化产品感知，而不是只做功能堆砌。
2. 工作区数据已支持本地持久化，但还需要更完整的业务字段来支撑协作与排期。
3. 生命周期动作已覆盖创建、复制、归档、回收与恢复，但需要更稳定的排序、筛选和批量操作体验。
4. 系统状态、活动流、摘要指标已经成形，但应进一步体现“可运营、可观察、可恢复”。
5. README 与目标文档必须持续反映当前产品能力，避免实现领先于文档。

## 本轮最终目标

把项目收敛为“面向真实写作工作流的本地产品控制台”，而不是一个只能演示单点能力的玩具样例。

## 验收标准

### 1. 产品入口
- 根路径 `/` 必须是稳定的产品首页，而不是直接落到临时会话。
- 首页必须提供新建、恢复最近工作区、模板起步、系统状态与最近活动入口。
- 首页必须支持搜索、筛选、排序、保存视图与批量动作。

### 2. 工作区持久化
- 工作区数据必须持久化到本地 `.data/workspaces/`。
- 应用重启后，标题、正文、标签、状态、活动记录等核心信息必须可恢复。
- 自定义字段 `owner`、`priority`、`due_at` 也必须持久化并兼容旧数据读取。

### 3. 生命周期与运营能力
- 至少支持创建、重命名、复制、置顶、归档、恢复、放入回收站、恢复回收站、永久删除。
- 批量动作至少支持状态流转、标签增删替换、负责人设置、优先级设置、截止日期设置与清空。
- 过期回收站项目必须自动清理，避免数据长期堆积。
- 排序结果必须稳定、可预期，特别是回收站到期时间与截止日期排序。

### 4. 工作区信息密度
- 工作区卡片必须展示标题、摘要、更新时间、标签、模板、引用数、版本数等基础信息。
- 工作区卡片必须展示负责人、优先级、截止日期，以及是否逾期。
- 工作区列表必须支持按 `owner`、`priority`、`label`、`status`、关键字进行组合过滤。

### 5. 视图与摘要
- 保存视图必须能够记住 `status / q / label / owner / priority / sort` 条件。
- 首页摘要必须体现总量、活跃、评审队列、已就绪、已分配、高优先级、逾期、标签规模等指标。
- 内置视图至少覆盖全部工作区、评审队列、就绪队列、高优先级、紧急、归档、回收站等常见场景。

### 6. 可观察性
- 提供 `GET /healthz` 与 `GET /api/system/status`。
- 首页必须可见模型、数据目录、工作区目录、RAG 论文数量、回收站数量等状态。
- 最近活动流必须体现跨工作区的重要动作，帮助定位最近发生了什么。

### 7. 文档一致性
- `README.md` 必须反映产品首页、工作区管理、批量动作、自定义字段与保存视图能力。
- 本文档必须作为本轮产品化改造的目标定义继续保留在仓库中。

## 非目标

- 不重写现有写作核心流程、RAG 主链路或导出架构。
- 不为了“产品感”引入新的外部基础设施依赖。
- 不顺带修复与本轮工作区产品化无关的历史问题。

## 完成定义

当以下条件同时满足时，本轮产品化可视为完成：

- 定向测试与相关回归测试通过。
- 相关文件静态检查通过。
- 首页、API、持久化、保存视图与文档对 `owner / priority / due date` 能力保持一致。
- 排序、批量动作与回收站清理在真实使用路径上可稳定工作。
